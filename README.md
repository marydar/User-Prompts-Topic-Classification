## Overview

This document describes the final topic classification system designed to automatically categorize user prompts (short, informal text queries) into one of 35 fine-grained topic labels organized under 10 parent categories. The system follows an **embed-then-classify** paradigm: raw text is first converted into dense vector representations using a pre-trained sentence transformer, and a lightweight logistic regression classifier is trained on top of these embeddings. A key innovation of this work is the use of **confidence-based filtering** at inference time, which trades coverage for accuracy by retaining only predictions where the model demonstrates high certainty.

---

## Problem Statement

User prompts arriving at large language model interfaces span a wide range of domains - from programming and cybersecurity to medicine, finance, law, sports, and the arts. An effective topic classifier must:

1. Handle short, informal, sometimes ambiguous text inputs.
2. Distinguish between 35 fine-grained sub-topics that can be semantically close (e.g., "Criminal Law" vs. "Family Law" vs. "Corporate Law" vs. "Civil Law").
3. Provide reliable confidence estimates so that uncertain predictions can be flagged or routed to alternative processing pipelines.
4. Operate efficiently at scale with low inference latency.

The approach chosen here addresses these requirements by combining a powerful pre-trained embedding model with a simple, interpretable classifier and a principled filtering mechanism based on prediction probability distributions.

## Dataset

### Source

The dataset is hosted on HuggingFace as `maryamdar/topic_classification_dataset_gen`. It contains approximately 19,935 labeled text samples, each representing a user prompt associated with one of 35 topic labels.

### Data Composition

Each sample in the dataset contains the following fields:

| Field | Description |
|-------|-------------|
| `text` | The raw user prompt text |
| `label` | The fine-grained topic label (one of 35 classes) |
| `parent_label` | The parent category (one of 10 categories) |
| `generator_model` | The LLM that generated the prompt |
| `source` | Origin of the sample (e.g., "generated") |
| `generation_group` | The prompting strategy used to generate the sample |
| `use_for_train` | Boolean flag indicating whether the sample should be used for training |

### Data Quality Steps

Before training, the following preprocessing steps are applied:

1. **Filtering by training flag**: Only samples where `use_for_train` is `True` are retained. This ensures that samples designated for validation or other purposes are excluded from the training pipeline.

2. **Filtering by generator model**: Samples generated by "MiMo V2.5 Free" are excluded. This is a deliberate decision to remove data produced by a specific model, likely because the classifier is intended to operate on prompts from other sources, or because the quality of prompts from this particular generator was deemed insufficient or biased.

3. **Dropping missing values**: Rows with missing `text` or `label` values are removed.

4. **Deduplication**: Exact duplicate text entries are removed, keeping only the first occurrence.

### Class Distribution

The dataset exhibits a relatively balanced distribution across the 35 labels. The largest class ("Desktop & Mobile & Web Development") accounts for approximately 6.6% of the data, while the smallest class ("Criminal Law") accounts for approximately 1.7%. This moderate imbalance is handled naturally by the logistic regression classifier without requiring explicit resampling techniques, as the imbalance is not severe enough to cause significant bias.

## Methodology

### 1. Data Loading and Preprocessing

The pipeline begins by loading the dataset from HuggingFace using the `datasets` library. The data is loaded directly into a Pandas DataFrame for inspection and manipulation.

**Key observations from exploratory analysis:**

- **Missing values**: The `old_label` and `old_parent_label` columns contain significant numbers of missing values (12,642 out of 19,935), but these are legacy fields and not used in the current classification pipeline. The critical columns (`text`, `label`, `parent_label`) have zero missing values.

- **No duplicate texts**: After filtering, no exact duplicate text entries remain in the dataset.

- **Label coverage**: All 35 labels are represented in the dataset, with sample counts ranging from approximately 341 (Criminal Law) to 1,315 (Desktop & Mobile & Web Development).

### 2. Label Taxonomy

The classification system employs a two-level hierarchical taxonomy:

**35 Fine-Grained Child Labels:**

The leaf-level labels represent specific topic domains. These are organized into an ordered list (`LABEL_ORDER`) that maps each label to a unique integer ID (0 through 34). This fixed ordering ensures reproducibility across training runs and prevents label leakage from arbitrary dictionary ordering.

The 35 labels span the following domains:

- **Programming/Technology**: Desktop & Mobile & Web Development, Cybersecurity, AI / Machine Learning / Data Science, Infrastructure (DevOps, Cloud, Databases, Networking)
- **Medical**: Clinical Diagnosis Treatment & Surgery, Medication & Pharmacology, Mental Health, Healthcare Organizations/System/Hospitals, Nutrition
- **Finance**: Payments & Personal Budgeting, Investment/Markets & Cryptocurrency, Corporate
- **Science**: Physics/Mathematics, Chemistry, Biology
- **Sports**: Team Sports, Individual Sports, Fitness
- **Engineering**: Civil/Structural & Architecture, Mechanical & Electrical Engineering
- **Personal**: Family & Relationships, Personal, Travel
- **Business**: Marketing & Sales, Entrepreneurship & Startups, Management/Strategy & Human Resources
- **Law**: Criminal Law, Family Law, Corporate Law, Civil Law
- **Art**: Game, Film, Music, Literature, Painting

**10 Parent Categories:**

The `HIERARCHY` dictionary defines the parent-child relationships. This hierarchical structure is used for aggregated evaluation (reporting precision/recall/F1 at the parent level) and for analyzing cross-domain misclassification patterns. A reverse mapping (`CHILD_TO_PARENT`) is also constructed for efficient lookup.

### 3. Train/Test Splitting

The dataset is split into training and test sets using an **80/20 stratified split** with a fixed random seed (`seed=42`) for reproducibility.

**Stratification** is performed on the `label_id` column, ensuring that each of the 35 classes is represented proportionally in both the training and test sets. This is critical for obtaining reliable evaluation metrics, especially for classes with fewer samples.

The HuggingFace `datasets` library's `ClassLabel` type is used to enable stratified splitting. The `label_id` column is cast to `ClassLabel` before splitting.

**Resulting split:**
- Training set: ~15,948 samples
- Test set: ~3,987 samples

The stratification preserves the class distribution almost perfectly. For example, "Desktop & Mobile & Web Development" constitutes 6.60% of both the training and test sets.

### 4. Text Embedding

Rather than working with raw text or traditional features (e.g., TF-IDF), this system uses **dense sentence embeddings** from a pre-trained transformer model.

**Model choice: `BAAI/bge-small-en-v1.5`**

This is a compact, efficient sentence embedding model from the BGE (BAAI General Embedding) family. Key characteristics:

- **Architecture**: BERT-based (12-layer transformer encoder)
- **Hidden size**: 384 dimensions
- **Parameters**: ~33 million (small enough for efficient CPU inference)
- **Training**: Optimized for semantic similarity and retrieval tasks
- **Max sequence length**: 512 tokens

The model was selected as a balance between embedding quality and computational efficiency. Larger models (e.g., `BAAI/bge-large-en`) were considered but the small variant proved sufficient for this classification task.

**Embedding extraction process:**

1. **Tokenization**: Each text sample is tokenized using the model's associated tokenizer (`AutoTokenizer`), with padding, truncation, and a maximum length of 512 tokens.

2. **Forward pass**: The tokenized input is passed through the model in `torch.no_grad()` mode (no gradient computation) to obtain the raw model output, which contains token-level embeddings.

3. **Mean pooling**: Instead of using the `[CLS]` token embedding (which is the default for many BERT-based models), **mean pooling** is applied. This technique computes the average of all token embeddings, weighted by the attention mask, to produce a single sentence-level vector. Mean pooling is widely recognized as producing higher-quality sentence representations than `[CLS]` pooling, especially for models trained with contrastive learning objectives.

   The mean pooling formula is:

   ```
   sentence_embedding = sum(token_embeddings * attention_mask) / sum(attention_mask)
   ```

   where `attention_mask` is expanded to match the embedding dimensions.

4. **L2 Normalization**: The resulting sentence embeddings are L2-normalized, projecting them onto the unit hypersphere. This normalization is standard practice for embedding models trained with cosine similarity objectives and ensures that the embedding space has uniform magnitude.

5. **Batch processing**: Embeddings are extracted in batches of 32 samples for memory efficiency, using the HuggingFace `datasets` `.map()` function with `batched=True`.

The final output is a 384-dimensional dense vector for each text sample, stored as a NumPy array.

### 5. Classification Model

**Classifier: Logistic Regression**

A `LogisticRegression` classifier from scikit-learn is trained on the extracted embeddings with the following configuration:

- `max_iter=1000`: Ensures convergence for the optimization algorithm (LBFGS solver by default).
- `C=1.0`: The default regularization strength (inverse of regularization parameter).

**Why Logistic Regression?**

Logistic regression is chosen for several well-motivated reasons:

1. **Compatibility with embeddings**: When inputs are high-quality dense embeddings (as produced by modern sentence transformers), linear classifiers often perform comparably to or better than complex non-linear models. The embedding model has already learned the non-linear feature transformations; the classifier only needs to learn the decision boundaries.

2. **Probabilistic output**: Logistic regression naturally produces well-calibrated probability distributions over all classes via the softmax function. This is essential for the confidence-based filtering mechanism described later.

3. **Interpretability**: The model weights can be inspected to understand which embedding dimensions are most discriminative for each class.

4. **Computational efficiency**: Training completes in seconds, and inference is essentially a matrix multiplication - extremely fast for production deployment.

5. **Regularization**: The built-in L2 regularization (controlled by parameter `C`) helps prevent overfitting, which is particularly important when the number of features (384) is non-trivial relative to the number of training samples per class (~450 on average).

The notebook also contains a commented-out alternative approach using `SGDClassifier` with `partial_fit`, which would enable incremental/online learning and training loss visualization. However, the standard `LogisticRegression` was chosen for its simplicity and strong performance.

### 6. Confidence-Based Filtering

This is a central contribution of the approach. Rather than accepting all predictions at face value, the system applies filtering to retain only high-confidence predictions. Two complementary filtering methods are implemented:

#### Method 1: Confidence Threshold

The simplest approach: retain predictions where the maximum class probability (the model's confidence in its top prediction) exceeds a threshold.

**Configuration**: `CONFIDENCE_THRESHOLD = 0.7`

**Results**:
- Total test samples: 3,987
- Confident samples retained: 2,691 (67.49%)
- Filtered out: 1,296

This method effectively identifies samples where the model is highly certain, but at the cost of discarding roughly one-third of the test set.

#### Method 2: Probability Margin Filtering

A more nuanced approach that examines the **gap between the top two predicted probabilities**. The intuition is that a prediction is truly confident not just when the top probability is high, but when it is clearly separated from the runner-up.

**Mathematical formulation:**

For each sample, the classifier produces a probability distribution $P = [p_1, p_2, ..., p_{35}]$ over all 35 classes. The probabilities are sorted in ascending order, and the margin is computed as:

$$\text{margin} = p_{\text{top-1}} - p_{\text{top-2}}$$

where $p_{\text{top-1}}$ is the highest probability and $p_{\text{top-2}}$ is the second-highest probability.

**Configuration**: `MARGIN_THRESHOLD = 0.2`

**Results**:
- Total test samples: 3,987
- Selected samples: 3,595 (90.17%)
- Filtered out: 392

**Why margin filtering is preferred:**

The margin-based approach is more selective about *which* samples to reject. A sample might have a top probability of 0.55 (below the 0.7 threshold in Method 1) but still have a large margin (e.g., 0.35) over the second choice, indicating that the model's prediction is unambiguous even if the absolute probability is moderate. Conversely, a sample with a top probability of 0.75 but a very small margin (e.g., 0.05) over the second choice is genuinely ambiguous and should be filtered out despite meeting the absolute confidence threshold.

The margin threshold of 0.2 was chosen empirically to provide a good balance between coverage (retaining 90% of samples) and accuracy improvement.

**Comparison of the two methods:**

| Aspect | Confidence Threshold | Probability Margin |
|--------|---------------------|-------------------|
| Threshold | 0.7 (absolute) | 0.2 (relative gap) |
| Coverage | 67.49% | 90.17% |
| Interpretation | "How sure is the model?" | "How clear is the winner?" |
| Weakness | Rejects moderate-confidence but clear predictions | May retain high-confidence but close-call predictions |

In practice, the margin-based method (Method 2) is used for the final evaluation because it achieves substantially higher accuracy (96.52%) while maintaining high coverage (90.17%).

## Evaluation Framework

The evaluation is comprehensive and operates at multiple levels:

### Child-Level Evaluation

**Metrics computed:**
- **Accuracy**: Overall proportion of correct predictions.
- **Precision, Recall, F1-Score**: Per-class metrics computed for all 35 labels.
- **Macro F1**: Unweighted average of per-class F1 scores (treats all classes equally regardless of size).
- **Weighted F1**: Weighted average of per-class F1 scores (accounts for class size differences).

**Visualizations:**
1. **Confusion Matrix (raw counts)**: Shows absolute numbers of correct and incorrect predictions for each class pair.
2. **Confusion Matrix (row-normalized percentages)**: Each row sums to 100%, making it easy to see the recall for each class and the distribution of errors.
3. **Misclassification-Only Confusion Matrix**: The diagonal (correct predictions) is zeroed out, highlighting only the errors. This makes it easy to identify which classes are most frequently confused with each other.

### Parent-Level Evaluation

Since the 35 child labels are organized under 10 parent categories, the evaluation also aggregates metrics at the parent level. For each parent category, the minimum, average, and maximum precision, recall, and F1 scores across its child labels are reported.

This provides insight into:
- Which broad domains (e.g., Medical, Law, Art) the model handles well.
- Whether errors tend to stay within a parent domain (e.g., confusing "Criminal Law" with "Family Law") or cross domain boundaries.

### Parent-Level Misclassification Matrix

A specialized confusion matrix that maps child-level errors back to the parent level. For each misclassified sample, both the true and predicted child labels are mapped to their respective parents, and the error is counted at the parent level. This reveals cross-domain confusion patterns (e.g., does the model confuse Medical samples with Science samples?).

## Model Export and Deployment

The trained model and associated metadata are saved for production deployment:

1. **Classifier model**: Saved as `classifier.joblib` using scikit-learn's joblib serialization. This file contains the complete trained logistic regression model, ready for inference.

2. **Label mappings**: Saved as `label_mappings.json`, containing the mapping from integer IDs to human-readable label names. This ensures that predictions can be decoded correctly without needing the original code.

**Inference pipeline (for deployment):**

1. Load the tokenizer and embedding model (`BAAI/bge-small-en-v1.5`).
2. Load the trained classifier (`classifier.joblib`).
3. Load label mappings (`label_mappings.json`).
4. For each new text sample:
   a. Tokenize the text.
   b. Pass through the embedding model with mean pooling and L2 normalization.
   c. Feed the 384-dimensional embedding into the classifier.
   d. Obtain probability distribution over 35 classes.
   e. Compute the margin between top-1 and top-2 predictions.
   f. If margin >= 0.2, accept the prediction; otherwise, flag as uncertain.

## Conclusion

The topic classification system presented in this notebook demonstrates that a well-designed embed-then-classify pipeline can achieve high accuracy on a challenging 35-class text classification problem. The key design decisions and their contributions to performance are:

1. **Pre-trained sentence embeddings** (`BAAI/bge-small-en-v1.5` with mean pooling) provide rich, semantically meaningful representations that capture the topical content of short, informal user prompts. The choice of a compact model (384 dimensions) ensures efficient inference without sacrificing quality.

2. **Logistic regression** serves as an effective and efficient classifier on top of the embeddings. Its natural probabilistic output enables the confidence filtering mechanism, and its simplicity makes the system easy to interpret and maintain.

3. **Probability margin filtering** is the most impactful technique for improving prediction reliability. By examining the gap between the top two predicted probabilities rather than relying on absolute confidence, the system achieves 96.52% accuracy on 90.17% of the test set - a practical operating point for production deployment where high reliability is essential.

4. **Hierarchical evaluation** at both the child (35-class) and parent (10-class) levels provides a complete picture of model performance, revealing both strengths (e.g., Medical domain) and areas for improvement (e.g., Business domain cross-category confusion).

The system is designed for practical deployment: the model files are serializable, the inference pipeline is straightforward, and the confidence filtering provides a natural mechanism for routing uncertain samples to alternative processing strategies (e.g., human review, ensemble methods, or larger models).
